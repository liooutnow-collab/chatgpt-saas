# L.I.O. Production Readiness Audit

Date: 2026-10-22

Scope: repository architecture, authentication/session handling, lead-search API, Supabase quota migrations, browser storage, deployment configuration, dependencies, public content, and available automated checks. No destructive or high-volume production tests were run.

## Baseline verified

- Repository: `liooutnow-collab/L.I.O`, branch `main`, clean before audit.
- Framework: Next.js App Router 16.4.0, React 19, TypeScript, Supabase SSR/Auth, Vercel deployment.
- Core routes: public marketing pages, login/auth callback, authenticated lead-search API, usage API, local browser search/result storage.
- Existing checks executed before edits: `npm run lint`, `npm run build`, and `npm audit --omit=dev --audit-level=moderate`.
- Baseline result: lint passed, production build passed, dependency audit reported 0 vulnerabilities.
- No automated unit, integration, end-to-end, accessibility, load, backup/restore, or cross-user isolation test suite was present in `package.json`.

## Architecture and data-flow summary

The browser authenticates through Supabase SSR cookies. The lead-search route revalidates the session, validates the request, reserves usage through Supabase RPCs, calls the server-side lead directory integration, settles usage, and stores an idempotent result payload in a private reservation record. Search history, lead records, saved leads, preferences, and formatter choices are currently stored in account-scoped browser local storage. The browser receives normalized lead results; Supabase stores quota and reservation state.

## Findings by severity

### Critical — quota settlement RPC is directly callable by authenticated clients

**Affected component:** `supabase/migrations/20261012210000_weekly_lead_entitlements.sql`, public `settle_discovery_quota` wrapper and grants; lead-search route.

**Evidence:** The migration grants `execute` on `public.settle_discovery_quota(uuid, integer, jsonb)` to `authenticated`. The function accepts `p_actual_count` and a client-supplied result payload, checks only that the result array length matches the claimed count and that the count does not exceed the reservation. It does not prove that the result was generated by the server-side directory call. A signed-in client can reserve a search and directly settle it with `p_actual_count = 0`, releasing the reservation without consuming lead units, then repeat.

**Impact:** A user can bypass the intended discovery allowance and potentially increase provider/API spend or abuse the internal testing entitlement. This violates the requirement that quotas and entitlements be enforced server-side.

**Remediation:** Remove direct client execution of settlement and route settlement through a trusted server-only path, or add server-verifiable attestation that clients cannot forge. Do not rely on hidden UI or request fields.

### High — no general server-side request rate limiting

**Affected component:** `/api/leads/search` and `/api/usage`.

**Evidence:** Authentication and quota reservations exist, but there is no IP/user rate limiter or concurrency guard at the HTTP boundary. The quota system limits normal plan units, but it does not protect authentication, malformed requests, repeated retries, or future internal/high-limit accounts from request floods.

**Impact:** Resource exhaustion, provider cost spikes, and availability degradation are possible. A controlled load test was not run against production.

**Remediation:** Add a bounded server-side per-user/IP rate limit and a small concurrent-search limit, ideally backed by an external/edge limiter or a database primitive suitable for the deployment model.

### High — security headers are incomplete

**Affected component:** `next.config.ts`.

**Evidence:** Only an `X-Robots-Tag` header is configured for `/`. There is no explicit Content-Security-Policy, frame protection, MIME sniffing protection, Referrer-Policy, Permissions-Policy, or HSTS configuration in the application.

**Impact:** Defense-in-depth against clickjacking, content-type confusion, referrer leakage, and script injection is weaker than necessary. CSP requires validation against Supabase and external map/website flows before enforcement.

**Remediation:** Add safe baseline headers immediately (`X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options`/CSP frame-ancestors). Add HSTS only when all production domains are HTTPS. Roll out CSP in report-only mode first, then enforce after testing.

### Medium — browser local storage contains lead and contact data

**Affected component:** `lib/storage/local-storage.ts`, lead/search hooks, privacy copy.

**Evidence:** Search history, lead records, saved leads, contact details, preferences, and formatter state are persisted in browser local storage. Account IDs scope keys, but local storage is readable by any JavaScript executing in the origin and is not server-synchronized or centrally deletable.

**Impact:** An XSS compromise or shared-device access can expose prospect/contact data. Clearing data is browser-local and does not provide a server-side deletion workflow.

**Remediation:** For sensitive or multi-device use, move lead/search persistence server-side with RLS and add retention/deletion controls. Until then, document the limitation and avoid storing more data than needed.

### Medium — no automated authorization, replay, accessibility, or regression tests

**Affected component:** project test tooling.

**Evidence:** `package.json` has only `dev`, `build`, `start`, and `lint` scripts. No test runner or browser accessibility tooling is configured.

**Impact:** Cross-user isolation, quota replay behavior, keyboard/focus behavior, and error-state regressions are not continuously verified.

**Remediation:** Add targeted tests for API authentication, quota replay/settlement, account isolation, input validation, and key accessibility flows.

### Medium — privacy/legal readiness is incomplete

**Affected component:** `/privacy`, product copy, data flow.

**Evidence:** The application transmits search terms and lead-discovery requests to a server-side third-party directory integration and stores lead/contact data in local storage. The current privacy overview is brief and does not provide a complete retention/deletion/processor/subprocessor description, jurisdictional analysis, terms, cookie notice, or outreach compliance workflow.

**Impact:** Launch readiness depends on jurisdiction, users, lead-data provenance, and future outreach behavior. This is a legal review item, not a finding of non-compliance.

**Remediation:** Have qualified counsel review privacy notices, terms, data-processing roles, lawful basis, retention/deletion, and future email outreach/unsubscribe requirements.

### Low — public repository reveals implementation names

**Affected component:** public source repository and documentation.

**Evidence:** Provider implementation names and environment-variable names are present in repository code and README. Runtime API/UI responses are separately sanitized.

**Impact:** Anyone with repository access can infer the implementation. This is not a secret exposure, but it means runtime presentation cannot guarantee provider confidentiality if the repository itself is public.

**Remediation:** Keep secrets out of the repository, use private repository access if provider confidentiality is a contractual requirement, and treat provider identity as non-secret operational metadata.

## Positive controls verified

- Server routes revalidate the Supabase user session.
- Quota tables/functions use private schema, `security definer`, and `search_path = ''`.
- Internal entitlement table has no client grants and provisioning functions require `service_role`.
- Request body size, UUID, count, string length, and brief-shape validation exist.
- Search attempts use idempotency keys and user-scoped reservation lookups.
- Secrets were not found in tracked files; dependency audit returned 0 vulnerabilities.
- Public lead API responses use neutral source labels and opaque IDs.

## High-risk remediation plan

1. Close the directly callable quota settlement path while preserving the existing server flow; requires a trusted server execution mechanism and a deployment secret/configuration check.
2. Add baseline security headers without introducing a CSP that could break existing external integrations.
3. Add targeted regression checks for the changed authorization boundary and headers.

## Unverified / requires external evidence

- Supabase production migration state and actual grants were not queried from the project in this audit.
- Vercel environment-variable presence and production runtime headers were not independently fetched.
- No live user-account or cross-account test was run.
- No production load test, backup/restore test, or third-party provider contract/license review was run.

This report intentionally distinguishes repository evidence from assumptions and does not claim full security, legal compliance, or production readiness.

## Remediation completed in this pass

- Added `supabase/migrations/20261022143000_guard_zero_settlements.sql`, which rejects `p_actual_count < 1` through the authenticated settlement wrapper. The lead-search route now releases empty-result reservations explicitly before returning a user-safe no-results response.
- Added baseline security headers globally in `next.config.ts`: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Permissions-Policy`.
- Verification: `npm run lint` passed; `npm run build` passed; targeted assertions confirmed the SQL guard and header declarations; a local runtime `curl` confirmed all four headers; a production `curl` against `https://outreach-saas-lio-8f66.vercel.app/` confirmed all four headers.
- Deployment: Vercel production deployment `dpl_9eYxgMCbLwzRjkwowVNKtV17b7Rj` reached `READY` for commit `f57f785`.

## Important remaining activation step

The new SQL migration is committed and deployed with the application, but this sandbox has no Supabase CLI or management/service-role connection, so the migration was not applied directly to the Supabase project during this pass. The quota guard is therefore verified in source and build/runtime checks but remains **pending database migration application** in the actual Supabase project. Until that migration is applied, treat the quota-settlement bypass as unresolved in production. The current Vercel project also has no server-only Supabase service-role key, so the stronger service-attested settlement design remains a future hardening task.
